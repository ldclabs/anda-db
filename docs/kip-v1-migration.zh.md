# 已发布 KIP 1.x 数据迁移指南

[English](kip-v1-migration.md)

Nexus 在打开其 v2 存储前会自动检测已持久化的 v1 集合结构。迁移过程自动执行，但在生产上线前，运维人员应当停止旧的写入进程，对对象存储进行一致性备份，并在副本上演练验证。迁移会就地替换原有的 `concepts` 与 `propositions` 两个图谱集合，属于单向变更；旧版本二进制不可作为回滚机制，若需回滚必须恢复迁移前的物理备份。

提取数据会先写入并刷新至 `kip_legacy_v1` 暂存集合，然后保存完成检查点。在删除任何旧集合之前，都会逐行比对核对暂存副本。若迁移过程发生中断或重启，系统会分别独立处理尚存的旧集合，绝不会删除已经构建完毕的 v2 集合。迁移后源数据行仍保留在暂存集合中，用于事后审计与灾难恢复。

数据加载阶段需等待宿主环境完成 Schema 激活。在正式安装前，生成的完整 Package 产物与精确的符号映射关系会一并持久化保存；重启时不会针对发生变化的环境重新猜测名称映射，也不会为已安装的 Package 生成不一致的字节。兼容包为 `kip://legacy/nexus@1.1.0`。

已发布的 v1 属性布局采用 `a` / `m` 缩写，迁移逻辑同时兼容恢复导出时所使用的长字段表示 `attributes` / `metadata`。`LegacyRecord` 完整保留源数据：包括 Concept 的原始记录行，或 Assertion 对应的每个谓词的源属性与旧身份标识。这些仅作为来源记录 (provenance)，不构成独立证据 (Evidence) 或治理授权。

- Person、Event、Preference、Insight、Commitment 和 SleepTask 均映射为兼容的原生类型。摘要、时间与任务字段完成标准化规范化；原处于 running、completed 或 failed 状态的 v1 任务在原生任务中统一转为 blocked，且不获取 v2 租约。其原始执行状态与执行结果完整保存在 LegacyRecord 中；原生任务需要显式人工或流程复核，绝不会自动恢复执行或获得虚构租约。
- Commitment 的 `completed` 映射为 `fulfilled`（这与 SleepTask 的执行状态处理不同）。对于此前迁移中属性尚未被修改的历史记录，数据库在打开时执行一次受属性版本保护的校正；用户后续编辑的内容及原始 LegacyRecord 内容保持不变，已归档记录继续维持归档状态。
- 与原生字段类型不兼容的可选值保留在 LegacyRecord 中。无法安全兼容的旧学习或运行时产物赋予独立的 Legacy 类型，保留其原始数据内容但不授予经过验证的正式语义地位。生成的类型名称避免与现有词汇表冲突。
- 关系元组两端节点若满足宿主谓词约束，则保留该谓词；不符合新约束的旧关系使用独立的 Legacy 谓词，符合约束的关系则保留在宿主常规查询使用的标准词汇表中。
- 导入的主张 (claims) 保留其记录的置信度 (confidence) 与可解析的归因信息。归因未知的记录归为迁移 actor 并保留原始文本描述。绝不会凭空捏造经过认证的 ActorBindings、来源信任度或旧系统中未记录的观察事实。
- 有效期映射为 `valid_time`，过期时间映射为保留期 (retention)。置顶状态 (pinning) 与助记记忆强度与认识论置信度分别独立保存，绝不将 confidence 混同为记忆强度。
- 归因明确的已知撤回记录将被完整重建。原生替代关系 (supersession) 要求同一 actor 针对同一 Proposition 存在可重构的无环修订链。跨 Proposition 的变更以及存在歧义的排除主张连同其注释一同归档，不会作为当前正面有效信念重新激活。原生状态转换按修订顺序依次应用，且在写入完成标记之前支持安全重试。

格式错误的标识符与悬空引用仍会导致迁移被拒绝。此时应检查错误定位的具体源数据行，并在备份副本上进行修复与验证演练。打开数据库失败并不意味着源存储为空。通用的 `migrate::plan` 仅用于资源清点；在正式切换至生产环境前，必须完整演练目标宿主的实际 Schema 和应用启动流程。

Anda Brain 的回归验证固件是基于 Brain v0.11.0 的 lockfile 中所发布的 Nexus/KIP 0.11.0 与 AndaDB 0.11.1 版本生成的完整对象存储快照。应用层专用的会话队列、缓存及内部记账逻辑仍由宿主自行维护。旧存储中较宽的历史会话字段仍可正常读取，并支持在不发生截断的前提下仅更新状态；新写入的字段则必须严格遵守当前的结构准入大小限制。
